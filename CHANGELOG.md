## [Unreleased]

### Added

- Project scaffolded from the n8n community node CLI template (agent docs, CI/publish GitHub Actions workflows, Prettier config, VS Code launch config)
- SAP Business One Service Layer node with light/dark icons, `usableAsTool` support, and a subtitle showing the selected operation and entity set
- Local HTTPS development tooling (`scripts/setup-local-n8n.mjs`) that resolves the local IPv4 address and generates a self-signed certificate with a matching IP SAN, plus `setup:local`/`dev:local` npm scripts and the `dotenv-cli` dependency, so the Service Layer webhook flow can be developed against `https://` locally
- `package.json` manifest declaring the SAP Business One Service Layer node, pinned dev dependencies, the Node `>=24.14.0` engine requirement, and project metadata (author, description, repository)
- `README.md` documenting the pre-production status, local HTTPS development workflow, planned Service Layer operations and credential fields, compatibility, and the SAP/n8n trademark disclaimer
- `SECURITY.md` with vulnerability reporting instructions, supported versions, and secret-handling guidance
- `CONTRIBUTING.md` documenting the current closed contribution model
- SAP Business One Service Layer API credential (`sapBusinessOneServiceLayerApi`) with a host-and-port base URL (the `/b1s/v2` Service Layer API path is added automatically), user name, password, company database, and TLS certificate validation fields, a `/Login` connection test that honours the certificate setting, the node's light/dark icons, and registration in `package.json` and on the Service Layer node
- Internal Service Layer session handling (`nodes/SapBusinessOneServiceLayer/helpers/`) that authenticates once per credential via `POST /Login`, caches and reuses the `B1SESSION` session, preserves and refreshes `ROUTEID`, treats the server-provided `SessionTimeout` as an idle timeout without assuming a lifetime of its own, collapses concurrent logins for the same credential onto a single request, discards sessions the Service Layer reports as invalid and retries the failed request once, and keeps passwords, session cookies, and response headers out of node output, logs, and error messages
- Metadata-driven foundation for the Service Layer node: a dependency-free, regex-based parser for the authenticated `/$metadata` (EDMX) endpoint that resolves entity sets to their entity types, simple and composite keys, properties, bound Actions/Functions, and unbound `ActionImport`/`FunctionImport` operations, rejecting metadata from the older, incompatible Service Layer v1 API with a clear error instead of silently omitting actions/functions; an in-memory metadata cache keyed by Service Layer instance and company database (shared across SAP users, one-hour TTL) with single-flight deduplication of concurrent fetches, reusing the existing session/request layer unchanged; a shared OData literal encoder for entity keys and operation parameters; and a `Resource` selector (`Entity Set`, `Service Operation`, `Custom API Call`) with a metadata-driven `Entity Set` dropdown — only `Entity Set` is scaffolded so far, and no operation executes against it yet, replacing the earlier placeholder `test` operation
- Entity Set CRUD operations: `Get`, `Get Many`, `Create`, `Update`, and `Delete`, driven entirely by the connected instance's metadata. `Get`/`Update`/`Delete` identify the entity through a metadata-driven `Key Fields` mapper — one input per key property, labelled with the property's own name (e.g. a single `ItemCode` field for `Items`, or `ItemCode`/`CardCode`/`Substitute` for the three-part composite key of `AlternateCatNum`) — validated against metadata before any request is sent and encoded as OData literals, percent-encoded so that key values containing URL-significant characters (`#`, `?`, `/`, spaces) address the right entity; `Create`/`Update` use a separate metadata-driven field mapper for the entity's non-collection properties; `Get Many` supports `Return All`/`Limit`, requesting the needed page size via the `Prefer: odata.maxpagesize` header (normally one request) and falling back to the Service Layer's `@odata.nextLink` pagination if a result is nonetheless split across pages. `$select`/`$filter`/`$orderby`/`$expand`, bound/unbound actions and functions, and collection/navigation properties (e.g. `DocumentLines`) in Create/Update bodies are not part of this release
- `Custom API Call` resource for calling any Service Layer endpoint through the existing authenticated request layer (login, `B1SESSION` reuse, expired-session retry, TLS setting, and error handling unchanged): an HTTP `Method` (`DELETE`, `GET`, `PATCH`, `POST`, `PUT`), a free-text `Endpoint` relative to the `/b1s/v2` API root with query parameters written inline, and an optional `JSON Body` for `POST`/`PATCH`/`PUT` that fails with a clear error when it is not valid JSON. Absolute and protocol-relative URLs, `..` path segments (including percent-encoded ones), and the `Login`/`Logout` endpoints are rejected before any request or login is made, so the session is never sent to another server, exposed in the output, or ended by a workflow. Each input item yields one output item: object responses are returned unchanged (collections are not split or paginated), empty responses return `{ success: true, statusCode }`, and any other response is returned under `data`. `continueOnFail()` is supported
- `Service Operation` resource for calling unbound Service Layer Actions and Functions picked from the connected instance's metadata: a `Service Operation` dropdown labelled with each operation's kind (e.g. `CompanyService_GetCompanyInfo (Function)`), and a metadata-driven `Parameters` mapper in which simple (`Edm.*`) parameters get typed fields and complex and collection parameters get JSON object/array fields. All parameters are optional, since the metadata marks none as required, and empty fields are not sent. Actions are sent as `POST` with a JSON body; Functions as `GET` with their parameters inline as type-aware OData literals. Invalid or wrongly shaped JSON fails with a clear error before any request. Requests use the existing authenticated request layer, and the output follows the `Custom API Call` convention. `continueOnFail()` is supported
- `Execute Action or Function` operation on the `Entity Set` resource for calling Actions and Functions bound to one entity, such as `Orders(45)/Close`: an `Action or Function` dropdown listing only the operations bound to the selected entity set's entity type (shared names such as `Close` resolve to the selected type), labelled with their kind; the entity identified through the existing `Key Fields` mapper, including composite keys; and the `Parameters` mapper of the `Service Operation` resource. Actions are sent as `POST /<EntitySet>(<key>)/<Action>`; Functions as `GET /<EntitySet>(<key>)/<Function>` without parentheses and with their parameters as OData literal query options, the form the Service Layer accepts for bound functions. For `SQLQueries` `List`, the `ParamList` value is sent as the stored query's own parameters (`code='C20000'&minTotal=100`), since the Service Layer rejects `ParamList` itself. The output follows the `Custom API Call` convention. `continueOnFail()` is supported
